# Control-path evidence legibility — an evaluation protocol

**Version:** draft-0.2 · **Date:** 22 August 2026 · **Status:** first-party, not independently reproduced

> draft-0.2 supersedes draft-0.1 (6 August 2026). The change is claim hygiene,
> not method: the third case is renamed to what it actually measures
> (an evidence-sink write failure, not a measured non-delivery), the
> acknowledgement-based scoring fallback is removed, and the baseline is
> described as what it is — a constructed comparison shape, not the output of
> a real logging implementation.

## The question

What can a reader conclude, from the record itself, about whether required
control and evidence observations were made? Concretely: when a record says an
action was allowed, blocked or recorded, what in that record establishes that
(1) the relevant check actually executed, (2) an evidence append that was
attempted actually succeeded, and (3) an action outside the governed path was
not represented identically to a governed one?

This is not a claim that agents behave badly, and not a containment claim. It
is a measurement of record representations: which represented conditions are
legible from which record shape, under a predeclared criterion.

## Design

Four fixed control-path conditions, each represented twice:

- **baseline posture** — a deliberately minimal, success-like record
  representation, used as the fixed comparison condition. It is constructed by
  this experiment; it is *not* the captured output of a real, separately
  deployed logging implementation.
- **instrumented posture** — a record representation in which measurement
  validity and the relevant control/evidence observations are explicit fields.

| # | Case | Provenance of the underlying condition |
|---|---|---|
| 1 | `check_not_executed` — the governance evaluator is never invoked | constructed semantic case |
| 2 | `policy_unavailable` — the policy the evaluator needs cannot be read | **driven local failure** — a real missing-file `OSError` in a temp dir; the surrounding records are constructed |
| 3 | `evidence_sink_write_failed` — a block decision envelope is built and the append to the evidence sink fails | **driven local failure** — the released `phionyx-mcp-server` 0.2.1 evidence writer against a `chmod 500` sink raises a real `OSError`; the surrounding records are constructed |
| 4 | `tool_path_bypassed` — the action reaches the world outside the governed tool path | constructed semantic case |

Even in the two driven cases, only the named local failure is real; both the
baseline and instrumented record shapes around it are generated by this
experiment. Each constructed element says so in its record's `provenance`
field.

Case 3 is an **evidence-persistence failure**, not a measured delivery
failure: what is observed is that an attempted append to a filesystem evidence
sink did not succeed (`evidence_persistence: attempted=true, succeeded=false`,
with the real `OSError`). No cross-process or cross-container delivery
round-trip to an enforcement point is exercised anywhere in this experiment,
and no external effect is observed. The distinctions stay separate throughout:
decision recorded ≠ delivery observed ≠ enforcement observed ≠ effect
observed.

## Scoring

One binary score per sample, under a predeclared criterion: **is the
represented failure or non-measurement condition legible from this record
alone?**

A record is legible when it declares a non-measurement or measurement error
(`measurement_status` ∈ {`NOT_MEASURED`, `ERROR`, `INCONCLUSIVE`}), records an
evidence append that was attempted and did not succeed, or marks the path as
ungoverned (`governed_path=false`). A success-like completion status is *not*
legibility — `status: completed / result: ok` is exactly what a healthy run
looks like.

The criterion deliberately draws no inference from acknowledgement fields.
`acknowledgement_recorded=false` establishes only that the representation
contains no acknowledgement observation; it does not establish non-delivery,
non-arrival, or enforcement failure, and it is not scored. (draft-0.1 scored
an acknowledgement-based fallback; it was never load-bearing — every
instrumented case is legible for an independently supported reason — and it
overstated what a missing acknowledgement establishes, so it was removed.)

## Result (fixture-local, rerun 22 August 2026)

| Posture | Legible conditions |
|---|---|
| baseline | **0 / 4** |
| instrumented | **4 / 4** |

Stated narrowly: under this experiment's predeclared legibility criterion,
none of the four represented failure/non-measurement conditions is legible
from the fixed baseline representation, while all four are legible from the
instrumented representation. This is a property of these fixed record shapes
and this criterion. It licenses no conclusion about execution logs in general,
Inspect logs in general, control systems in general, or any deployed agent
system.

The baseline representation can support false assurance **if** its
success-like completion fields are interpreted as evidence that the relevant
control property was actually measured — that conditional is the exact scope
of the claim.

Artefacts: `out/logs/baseline.eval`, `out/logs/instrumented.eval`.

## Role of Inspect

Inspect AI's `.eval` format is used as a **serialization/replay container**:
the experiment writes its logs through Inspect's public log API
(`inspect_ai.log`, pinned 0.3.252) and reads them back with Inspect's own
reader as part of the run. This experiment does not test, and establishes
nothing about, Inspect, ControlArena, or any institution's evaluation
practice — including whether Inspect has or lacks a canonical representation
for these distinctions. No conclusion about AISI, Inspect or ControlArena
follows from this artefact.

## Reproduction

```bash
bash control_delivery_eval/reproduce.sh
```

Pinned: `phionyx-mcp-server==0.2.1`, `inspect-ai==0.3.252`. The experiment uses
no network and calls no model; the only network use is pip installing those two
packages into a throwaway virtualenv. It writes nothing outside that venv and
`out/`. Runtime: seconds.

View interactively: `inspect view --log-dir control_delivery_eval/out/logs`

## Explicit limits

1. **First-party.** Nothing here has been independently reproduced. The value
   of the artefact is that the method is executable by someone else, not that
   it has been.
2. **No model or agent is in the loop.** The subject is the record
   representation, not behavior.
3. **Both record shapes are constructed by this experiment.** The baseline is
   a fixed minimal comparison shape, not the output of a real, separately
   deployed logging implementation.
4. **Only two of the four underlying conditions are actually driven** (missing
   policy file; unwritable evidence sink). The other two are constructed
   semantic cases, marked as such in their `provenance` fields.
5. **No real cross-process / cross-container delivery round-trip to an
   enforcement point is exercised.**
6. **No external effect is observed.** Observing effect needs a separate
   observer, which this experiment does not have.
7. **Absence of an acknowledgement observation does not prove non-delivery.**
   The scoring draws no inference from acknowledgement fields.
8. **A delivery record would not by itself prove enforcement or material
   effect.** Decision recorded ≠ delivery observed ≠ enforcement observed ≠
   effect observed; a record asserting all four would still be a record, not
   the effect.
9. **Inspect is a log container/reader here, not the subject under
   evaluation.**
10. **No conclusion about AISI, Inspect or ControlArena follows from this
    experiment.**
11. **The instrumented shape is not claimed to be emitted end-to-end by any
    shipped Phionyx runtime.** The non-measurement vocabulary exists in
    `phionyx_core/pipeline/outcome.py` (`BlockOutcome`) and in the released
    chain verifier; the `control_delivery` and `evidence_persistence`
    structures used here are constructed by this experiment. AIREP's v0.1
    `control_delivery` profile distinguishes an instruction-delivery lifecycle
    (`issued / delivered / acknowledged / enforced / observed /
    delivery_failed`) with its own field vocabulary; the fixture's boolean
    structure is thematically related to it but is not an AIREP record and
    does not validate against that profile.
12. **The evidence formats in this project do not currently interoperate, and
    this experiment does not depend on their doing so.** Measured 2026-08-06:
    an envelope produced by the released `phionyx-mcp-server` 0.2.1 writer is
    rejected by AIREP's own reference verifier (`FAIL(schema,hash)`). The two
    formats are related by intent, not by a working projection. Nothing in
    this protocol should be read as a claim that Phionyx emits AIREP records.
